## Быстрый старт

Нужен Python 3.11. Проверка: `python3 --version`.
Если Python не стоит, версия другая или у вас Windows — сначала [docs/setup.md](docs/setup.md), там пошагово по операционным системам.

```bash
# 1. клонировать свой форк (как его сделать — в ДЗ-1)
git clone https://github.com/<ваш-логин>/ml_learning_course.git
cd ml_learning_course

# 2. создать виртуальное окружение и активировать
python3 -m venv .venv
source .venv/bin/activate        # macOS / Linux / WSL
.\.venv\Scripts\Activate.ps1     # Windows PowerShell

# 3. поставить зависимости
pip install --upgrade pip
pip install -r requirements.txt

# 4. зарегистрировать окружение как ядро Jupyter
python -m ipykernel install --user --name ml-course --display-name "Python (ml-course)"

# 5. создать файл с доступами к базе
cp .env.example .env

# 6. проверить, что всё живое
python -c "import sys; print(sys.executable)"
python -c "from src.db import get_client; print(get_client().query('SELECT version()').result_rows)"
```

После шага 2 в начале строки терминала появится `(.venv)`. **Если его нет — окружение не активировано**, и `pip install` поставит библиотеки мимо проекта. Это причина примерно половины проблем на этом модуле.

## Структура проекта

Что здесь лежит и зачем каждый файл. Это не формальность: по этому списку вас будут спрашивать, и ровно эту структуру вы потом воспроизводите в своих проектах.

```
ml_learning_course/
├── notebooks/          ноутбуки: задания и ваши решения
├── src/                переиспользуемый код проекта
│   └── db.py           подключение к ClickHouse
├── data/               локальные данные, в git не уезжают
├── docs/
│   └── setup.md        установка окружения по операционным системам
├── .env                ваши доступы к базе. НЕ в git
├── .env.example        шаблон доступов. В git
├── .gitignore          что git обязан игнорировать
├── requirements.txt    список библиотек с версиями
├── .python-version     версия Python для проекта
├── CLAUDE.md           правила проекта для AI-агента
├── .claude/settings.json  что агенту можно, а что нельзя
└── README.md           этот файл
```

**`notebooks/`** — ноутбуки. Задание (`hwNN_task.ipynb`) приезжает от преподавателя, решение (`hwNN_solution.ipynb`) пишете вы. Ноутбук нужен для исследования и графиков — то есть для того, что вы смотрите глазами один раз.

**`src/`** — код, который нужен больше одного раза. Правило проекта: **написали функцию второй раз — переносите её сюда.** Иначе через месяц у вас пять слегка разных версий одной функции и непонятно, какая правильная. Сейчас здесь только [`src/db.py`](src/db.py) — он читает доступы из `.env` и отдаёт готовый клиент ClickHouse, чтобы вы не писали параметры подключения в каждом ноутбуке.

**`data/`** — данные лежат локально и в git не попадают: они тяжёлые, часто чужие и иногда персональные. Git — не хранилище данных.

**`.env` и `.env.example`** — доступы к базе. Пароли **никогда** не пишутся в коде и в ноутбуке. Причина не в этикете: git запоминает всё навсегда, и пароль, закоммиченный один раз и стёртый следующим коммитом, достаётся из истории одной командой. Публичные репозитории сканируются ботами за минуты. Поэтому доступы живут в `.env`, который перечислен в `.gitignore`. Рядом лежит `.env.example` — тот же файл с пустыми/публичными значениями, он в git **специально**: по нему видно, какие переменные нужны проекту. Человек, который клонировал ваш репозиторий, делает `cp .env.example .env` и заполняет своими.

**`.gitignore`** — список того, что git обязан игнорировать: секреты (`.env`), мусор окружения (`.venv/`, `__pycache__/`, `.ipynb_checkpoints/`) и данные (`data/`). Проверить, что файл действительно игнорируется: `git check-ignore -v .env`.

**`requirements.txt`** — список библиотек с **жёстко зафиксированными** версиями (`pandas==2.2.3`). Само окружение в git не попадает — оно весит сотни мегабайт и у каждой ОС своё. В git попадает список того, что в нём должно быть. Если написать просто `pandas`, то сегодня встанет 2.2.3, а через полгода 3.0, где часть методов переименована, и проект перестанет запускаться сам по себе, без единой правки в коде. Правило: **поставили библиотеку — сразу дописали её сюда с версией.**

**`.python-version`** — версия Python для проекта. Код, написанный на 3.11, может не запуститься на 3.9, а `numpy 2.1` на 3.9 просто не установится.

**`CLAUDE.md` и `.claude/settings.json`** — обвязка для AI-агента. `CLAUDE.md` агент читает при каждом запуске: что за проект, какой стек, чего делать нельзя. `settings.json` — разрешения: что агент запускает сам, а что только с вашего подтверждения (`git push`, `rm -rf` и чтение `.env` запрещены — агент ошибается, и цена ошибки не должна быть «стёр папку» или «выложил пароль»). Агент полезен ровно настолько, насколько понятен проект: увидит одинокий ноутбук — будет угадывать.

## База данных

В домашке вы работаете с **публичным ClickHouse** — там лежит открытый датасет поездок такси Нью-Йорка. Регистрация, VPN и создание таблиц не нужны, доступы уже лежат в `.env.example`:

```
CLICKHOUSE_HOST=sql-clickhouse.clickhouse.com
CLICKHOUSE_USER=demo
CLICKHOUSE_PASSWORD=        # пусто, доступ только на чтение
```

Основная таблица — `nyc_taxi.trips_small`: 3 млн поездок за июль–сентябрь 2015 года.

Если хотите работать со своим сервисом ClickHouse Cloud, который заводили на SQL-модуле, — впишите в `.env` его host / user / password вместо публичных. Код менять не нужно: [`src/db.py`](src/db.py) берёт всё из `.env`.

Подключение из ноутбука — три строки, параметры руками нигде не пишем:

```python
from src.db import get_client

client = get_client()
print(client.query("SELECT version()").result_rows)
```

## Как сдавать домашку

Каждое ДЗ — отдельная ветка и отдельный pull request **внутри вашего форка**: из ветки `hw01` в вашу же ветку `main`. Проверяющий оставляет комментарии прямо в PR, вы правите и дописываете в ту же ветку.

```bash
git checkout -b hw01
# ... работаете ...
git add .
git commit -m "hw01: окружение и подключение"
git push -u origin hw01
```

Дальше на GitHub: **Compare & pull request** → заголовок `HW01`, в описании коротко, что сделали и где застряли.

> ⚠️ GitHub по умолчанию предлагает открыть PR в репозиторий преподавателя. В форме PR слева выберите **base repository = ваш форк**, иначе домашка уедет не туда.

**Перед каждым коммитом ноутбука:** Kernel → Restart Kernel and Run All Cells. Ноутбук, который не проходит сверху вниз с чистого ядра, домашкой не считается — на этом сыпятся проекты в портфолио.

Выводы ячеек в коммит не уезжают: в проекте есть `nbstripout`, он вырезает их автоматически. Включается один раз после клонирования:

```bash
nbstripout --install
```

## Если что-то не заводится

Порядок действий, прежде чем писать в чат:

1. `python -c "import sys; print(sys.executable)"` — путь ведёт внутрь `.venv` вашего проекта?
2. `pip list | grep clickhouse` — библиотека вообще стоит?
3. `cat .env` — переменные заполнены, без кавычек и без пробелов вокруг `=`?
4. Ядро ноутбука — **Python (ml-course)**?

Самая частая ошибка модуля: окружение создали, библиотеки поставили, а ноутбук пишет `ModuleNotFoundError`. Причина почти всегда одна — **ноутбук запущен на другом ядре**. Лечение: справа сверху в ноутбуке выбрать ядро **Python (ml-course)**.
